# VortexPHM-AI: Master Build Guide

One guide, from an empty folder to a deployed demo. Frontend, backend, models, integration, deployment, in numbered modules. Every module says what to do, which files to use, how to run it, and how to know it worked.

Legend: **[ready]** the code already exists in this repository and was tested as described in section 2. **[you run]** you run commands on your machine. **[real data]** needs the NASA files, which I could not run here.

## M0. Setup

**Goal:** a clean workspace on your Lenovo LOQ (Windows) that cannot choke on large files.

1. **Move the project out of OneDrive**, for example `C:\dev\VortexPHM-AI` (N-CMAPSS files are large and OneDrive will fight with them). If you must stay in OneDrive, exclude `data\`.
2. Install: Python 3.12 (3.13 usually works), Node 20+, Git, optionally Docker Desktop. Check with `python --version` and `node --version`.
3. Unzip this package into that folder and run `git init`, then `git add . && git commit -m "baseline"`.
4. Backend environment (PowerShell):
   ```powershell
   cd C:\dev\VortexPHM-AI\backend
   py -3.12 -m venv .venv
   .\.venv\Scripts\activate
   python -m pip install -U pip
   pip install -r requirements.txt
   ```
   For GPU training of the LSTM autoencoder install the CUDA build of PyTorch from pytorch.org instead of the default `torch` wheel.
5. Sanity check: `python -m pytest tests/test_core.py -q` should print `5 passed` (the API test is skipped until models exist).

**Common problems:** `ModuleNotFoundError: src` means you are not inside `backend/` (always run `python -m ...` from `backend/`). A wheel failing to install on Python 3.13 means use 3.12.

## M1. Get the data **[you run] [real data]**

**Goal:** the NASA files where the code expects them.

1. Open the NASA Prognostics Center of Excellence data repository and download:
   - **N-CMAPSS**: the `.h5` files (start with two or three DS files).
   - **C-MAPSS**: the four sets FD001 to FD004 (`train_FD00x.txt`, `test_FD00x.txt`, `RUL_FD00x.txt`).
2. Put them in `data/raw/ncmapss/` and `data/raw/cmapss/`.
3. Inspect each N-CMAPSS file **before building anything**:
   ```powershell
   python -m scripts.inspect_ncmapss ..\data\raw\ncmapss\<file>.h5
   ```
   It prints the column names, which health parameter degrades per engine (the fault module), cycles per engine and the `hs` health-state average.
4. Decide which files to use. You want **Fan, LPC, HPC and HPT** each present in at least about 3 engines, because cross-validation is split by engine. LPT-only engines are excluded from the classifier (still used for RUL and anomaly detection).

**What to verify against my assumptions:** column names `hs` (1 = healthy, 0 = degraded) and `*_mod` health parameters. If they differ, change `label_units` in `src/data_pipeline/build_dataset.py`.

**Common problems:** very large files exceed RAM. Raise `stride` in `load_ncmapss` (default 10 samples per flight sampled), or process one file at a time (already the case).

## M2. Data pipeline **[ready] [you run]**

**Files:** `src/data_pipeline/ingestion.py`, `regime_normalizer.py`, `quality_checker.py`, `features.py`, `build_dataset.py`.

**What each does**

| File | Responsibility |
| :--- | :--- |
| `ingestion.py` | Reads C-MAPSS text and N-CMAPSS `.h5`, builds engine ids, aggregates 1 Hz flights into one record per cycle (mean/std of each channel) |
| `regime_normalizer.py` | Aerodynamic correction from fan-inlet T2/P2 (θ = T2/518.67 °R, δ = P2/14.696 psia), per-regime z-scoring fitted on nominal training data only |
| `quality_checker.py` | Completeness, thermodynamic order checks (N-CMAPSS: P2<P24<P30, T2<T24<T30; C-MAPSS: P2<P15<P30, T2<T24<T30), stuck-sensor detection |
| `features.py` | Past-only rolling mean and slope (W = 10) |
| `build_dataset.py` | Orchestrates the above, labels engines, writes Parquet + quality report |

**Steps**

1. Build the C-MAPSS sets (repeat for FD002 to FD004):
   ```powershell
   python -m src.data_pipeline.build_dataset --dataset cmapss --subset FD001
   ```
2. Build N-CMAPSS:
   ```powershell
   python -m src.data_pipeline.build_dataset --dataset ncmapss
   ```
3. Open `results/quality_report_*.json`.

**Done when:** `passed: true`, completeness at least 0.9998, no physics violations, no stuck sensors. If a check fails, read which channel and either fix the data handling or document it (do not silence the check).

## M3. Sensor-drift injection and labels **[ready]**

**Files:** `src/data_pipeline/injector.py` and `label_units` in `build_dataset.py`.

**How labels are made**

- Fault class = the module with the largest health-parameter degradation per engine (fan and LPC merged into `FAULT_FAN_LPC`, HPC, HPT). Cycles before the unhealthy state are `NOMINAL`.
- `FAULT_SENSOR_DRIFT` is **synthetic**: virtual engines are copied from nominal segments of real engines, then a +0.05 %/cycle drift or a step bias is injected into one sensor channel, plus Gaussian noise at SNR ≥ 32 dB. Virtual engines inherit the split of their parent, so train and test never mix.

**Done when:** the build summary table lists all five classes in both `dev` and `test`. If a class is missing in `test`, add another DS file.

## M4. Detection models **[ready] [you run]**

**Files:** `src/models/train_models.py` (baselines and Isolation Forest), `src/models/lstm_ae.py`, `src/models/evaluation.py`.

**Concepts**

- Alarm = at least 3 of the last 5 cycles flagged (persistent alarm). False alarm = persistent alarm before degradation onset. Lead time = failure cycle minus first persistent alarm after onset.
- Thresholds are **calibrated** on held-out validation engines to a persistent-alarm false-alarm rate of at most 1 % (target is 2 %). A fixed 3-sigma rule is reported as the traditional-CBM baseline.

**Steps**

1. Train and benchmark on C-MAPSS first (lead time is most meaningful there):
   ```powershell
   python -m src.models.train_models --dataset cmapss_FD001
   ```
2. Train the LSTM autoencoder (uses the GPU if PyTorch sees it):
   ```powershell
   python -m src.models.lstm_ae --dataset ncmapss
   ```

**Done when:** `results/benchmark_*.json` contains `baseline_fixed_3sigma`, `baseline_calibrated`, `isolation_forest`, and `results/lstm_ae_ncmapss.json` exists.

## M5. Classifier and RUL **[ready] [you run]**

Same script. **Order matters:** the last dataset trained writes `backend/artifacts/`, so train N-CMAPSS last.

```powershell
python -m src.models.train_models --dataset cmapss_FD002     # optional extra benchmarks
python -m src.models.train_models --dataset ncmapss          # LAST: writes the serving artifacts
```

Outputs: `artifacts/clf.json`, `rul.json`, `iforest.joblib`, `meta.json` (feature list, thresholds, score scaling, RUL sigma). The XGBoost classifier uses class weights and engine-level cross-validation. The RUL model predicts a capped target (125 cycles) and stores validation-residual sigma for the uncertainty band.

**Done when:** `benchmark_ncmapss.json` has `classifier.test_macro_f1`, `test_macro_precision`, a confusion matrix and `rul.rmse_last_cycle`.

**If targets are missed** (macro-F1 below 0.91 or lead time below 35 cycles): do not leak to hit them. Try more DS files or engines per class, a longer rolling window (20), different persistence settings, and report honestly with the per-class breakdown, ablations and the "% of life" lead-time metric.

## M7. XAI and decision engine **[ready]**

**Files:** `src/xai/explain.py`, `src/decision_engine/{urgency,cost_model,amm}.py`.

| Piece | How it works |
| :--- | :--- |
| TreeSHAP | XGBoost `pred_contribs` (exact TreeSHAP in C++), top-3 and a 10-bar waterfall for the predicted class |
| Urgency | U = 100 · [0.35 S_anom + 0.35 S_crit + 0.30 (1 − RUL/125)]; tiers: ≥ 70 critical, 40–69 elevated, < 40 monitor |
| Cost-benefit | P(fail within 30 cycles) from RUL ± sigma times the UER cost, compared with inspection cost; **assumption-based constants in `cost_model.py`**, edit them |
| AMM tasks | Illustrative references per class (`amm.py`); label them illustrative |

**Tune:** open the urgency distribution on your validation engines and adjust the 70 and 40 thresholds in `urgency.py` if everything lands in one tier. Keep `Canonical_Parameters.md` in sync.

## M8. API and audit log **[ready]**

**Files:** `src/api/{main,service,db,schemas}.py`, `scripts/export_serving.py`.

1. Create the small demo fleet (a handful of test engines, not the raw data):
   ```powershell
   python -m scripts.export_serving
   ```
2. Run the API:
   ```powershell
   $env:CORS_ORIGINS="http://localhost:3000"
   uvicorn src.api.main:app --reload --port 8000
   ```
3. Open `http://localhost:8000/docs`.

| Route (under `/api/v1`) | Purpose |
| :--- | :--- |
| `GET /health` | engine count |
| `GET /decision/triage-queue?frac=0.75` | fleet ranked by urgency at a "fleet time" |
| `POST /diagnostics/evaluate` | one cycle: diagnosis, urgency, cost, AMM, TreeSHAP, sensor z-scores |
| `GET /engines/{id}/replay?speed=0` | Server-Sent Events: one diagnosis per cycle |
| `POST /decision/action` | ACCEPT / OVERRIDE / DEFER with licence ID and ≥ 50-char justification |
| `GET /audit`, `GET /audit/verify` | log and hash-chain verification |
| `GET /metrics/benchmark` | every JSON file in `results/` (used by the Models page) |

**Audit design:** each row stores `prev_hash` and `entry_hash = SHA-256(prev_hash | canonical payload)`; SQLite triggers block UPDATE and DELETE (PostgreSQL triggers are installed automatically when `DATABASE_URL` is a PostgreSQL URL). A unit test removes the trigger, edits a row, and checks that `/audit/verify` reports the broken entry.

**Done when:** `/docs` loads, a decision returns a hash, and `/audit/verify` returns `valid: true`.

## M10. 3D assets **[ready] (already generated)**

The finished assets are in `frontend/public`. The scripts in `frontend/tools` reproduce them.

1. **Model** (`tools/process_model.mjs`): maps the 29 named parts to stations (fan, lpc, hpc, combustor, hpt, lpt, nozzle, shaft), simplifies (296k → 110k triangles), merges materials, meshopt-compresses (0.9 MB). To re-run: `cd tools && npm install && node process_model.mjs <path-to>/scene.gltf ../public/models && node validate_model.mjs`. Edit the `STATION` table to change the part-to-station mapping.
2. **Frames** (`tools/process_frames.py`): removes the corner watermark by inpainting, trims the static head and tail (frames 8–285), writes a desktop set (120 × 1280×720 WebP, 5.9 MB), a mobile set (80 × 854×480, 2.0 MB) and a poster.
3. **Licences:** the frames come from an AI video generator (the star mark) and the GLB is from Sketchfab. Check both licences before publishing publicly. `public/models/CREDITS.txt` carries the credit. If you cannot publish the GLB, the viewer falls back to the 2D schematic, or replace it with a model you may redistribute.

## M15. Integration **[you run]**

Run everything together (three terminals):

```powershell
# 1  backend
cd backend ; .\.venv\Scripts\activate ; $env:CORS_ORIGINS="http://localhost:3000" ; uvicorn src.api.main:app --port 8000
# 2  frontend
cd frontend ; npm run dev
# 3  tests (optional)
cd backend ; python -m pytest -q
```

**End-to-end checklist**

1. `http://localhost:8000/api/v1/health` returns the engine count.
2. `http://localhost:3000/fleet` lists engines; the slider changes tiers.
3. Open an engine, press Replay: urgency climbs, the 3D engine tints, the first-alarm tick appears.
4. Pause, open **Explain**: top-3 drivers look physically plausible for the fault (for example HPT: T48 and T50 up).
5. **Decide**: a short justification keeps the button disabled; a valid one returns a hash.
6. **Audit** and the alert strip show the entry and "Chain verified".
7. `/models` shows your benchmark numbers (or the empty state).
8. Toggle light theme on the app pages; the landing page stays dark.

**Common problems:** CORS error in the browser console means `CORS_ORIGINS` does not include the exact frontend origin. A blank Models page means no JSON in `results/`. Engines missing on the fleet page means `export_serving` has not been run. The SSE stream failing behind a proxy: check that buffering is off (the API sends `X-Accel-Buffering: no`).

## M16. Docker, CI and deployment **[you run]**

**Local container run**

```powershell
docker compose up --build
```

**Deploy**

1. Commit `backend/artifacts/` (small) and `data/serving/fleet.parquet`. Keep `data/raw` and `data/processed` out of git.
2. **Backend:** a Docker web service from the repo root on a container host (Render, Railway or Fly.io; check each one's current free-tier memory, sleep behaviour and disk options first). Environment: `CORS_ORIGINS=https://<your-vercel-domain>` and **one** of: `DATABASE_URL=postgresql+psycopg://...` (managed PostgreSQL) or `AUDIT_DB=/data/audit.db` on a persistent disk. Without one of these the audit log disappears at every redeploy.
3. **Frontend:** Vercel, root directory `frontend`, environment variable `NEXT_PUBLIC_API_URL=https://<backend-url>/api/v1`.
4. Smoke test the public URLs with the M15 checklist.
5. **Presentation day:** free hosts sleep. Open `/api/v1/health` five minutes earlier. Keep a screen recording and a local `docker compose up` as backups.

**CI:** `.github/workflows/ci.yml` runs the core backend tests and a frontend type check on every push.

## M17. Demo and viva

**Seven-minute demo**

1. Landing (60 s): scroll the engine open, read the four chapters, "Open fleet board".
2. Fleet (45 s): drag the fleet-time slider so the board turns from calm to alarmed.
3. Cockpit (90 s): replay an engine; watch the urgency climb and the 3D station heat up; point at the first-alarm tick.
4. Explain (60 s): top-3 drivers, SHAP bars, latency chip.
5. Decide (60 s): short justification blocked, valid one sealed, hash shown.
6. Audit (30 s): chain verified. Optional: show the tamper test.
7. Models (45 s): your measured numbers against the targets, baseline vs ML, honest limitations.

**Likely questions and short answers**

- *Why N-CMAPSS as well as C-MAPSS?* Only N-CMAPSS has fault-mode ground truth and flight conditions; C-MAPSS gives comparability with the literature.
- *Is the sensor-drift class circular?* It is synthetic by design, injected on clean segments, split by parent engine, with different random draws in test.
- *Leakage?* Engine-level splits, past-only features, normalisation fitted on training nominal data only.
- *How is false-alarm rate defined?* Persistent-alarm share of pre-onset cycles, calibrated on validation engines, reported per cycle and per engine.
- *Certification?* Advisory prototype, not certified; human decision with a tamper-evident log.
- *Where do the cost numbers come from?* Stated assumptions in `cost_model.py`; the framework matters, not the constants.
- *Is the hero image your engine?* No, it is an illustrative render; the data is simulated NASA data.
